## Il geoinformation model

ArcGIS Enterprise è la spina dorsale del sistema ArcGIS che un'organizzazione installa e mantiene, e attraverso di essa si accede al **geoinformation model**: il modo in cui l'informazione geografica viene creata e condivisa. Sei componenti.

| Componente | Che cos'è |
|---|---|
| **Portal** | Collezione organizzata di item in un sito web personalizzato. Enterprise li ordina in gallerie: contenuti personali, di gruppo, dell'organizzazione. |
| **Maps and scenes** | Il quadro principale per visualizzare dati georiferiti. Le mappe mostrano dati **2D**, le scene aggiungono la terza dimensione e il controllo di luce, inclinazione e angolo di vista. |
| **Layers** | Collezioni logiche di dati geografici — centri abitati, strade, aree di pericolo. Sono la base di analisi, mappe e scene. |
| **Analytics** | Sintetizzare dati, trovare località, arricchire, analizzare pattern spaziali, esplorare la prossimità. Include un ampio insieme di funzioni di modellazione, per desktop e web, e la possibilità di creare strumenti custom. |
| **Apps** | Programmi mapcentrici con workflow e strumenti focalizzati su un pubblico specifico: desktop, mobile, web, o custom costruite sulle API ArcGIS. |
| **ArcGIS Living Atlas** | Collezione di contenuti globali forniti da Esri, combinabili con gli item della propria organizzazione. |

## Il base deployment

Il **base deployment** abilita quel modello su infrastruttura controllata dall'organizzazione, on premise o in cloud, e consiste di **quattro componenti software** che lavorano come un sistema unico.

| Componente | Ruolo |
|---|---|
| **Portal for ArcGIS** | Content management system con il sito web front-end per cercare, usare e condividere item. Contiene le app integrate: **Map Viewer** per le web map, **Scene Viewer** per le scene, **Instant Apps** ed **Experience Builder** per le web app. |
| **ArcGIS Server** | Risponde alle richieste dei client che usano item basati su servizi: zoom di una web map, ricerca di una località, esecuzione di uno strumento di analisi. Per poter pubblicare, un Server deve essere designato **hosting server**. |
| **ArcGIS Data Store** | Configura l'archiviazione per l'hosting server. È il repository di default per i **feature layer 2D ospitati** (relational data store) e per gli **scene layer 3D** (tile cache data store). |
| **ArcGIS Web Adaptor** | Componente amministrativo che integra Portal, Server, i web server dell'organizzazione e i suoi meccanismi di sicurezza. |

### La federation, e perché produce due cose

Il modello di sicurezza e condivisione del portale è integrato con ArcGIS Server attraverso una relazione chiamata **federation**. La conseguenza va tenuta a mente perché spiega metà dei fraintendimenti successivi: pubblicando una risorsa GIS verso Enterprise vengono creati **automaticamente sia un item del portale sia il servizio web associato**.

Sono due strati, e non coincidono. L'item è ciò che si cerca, si descrive e si condivide; il servizio è ciò che risponde alle richieste. Un item **può anche non avere un servizio**, come si vede subito qui sotto.

## Portare contenuti nel portale

Tre modi per creare item direttamente dal portale, senza passare da ArcGIS Pro: caricare un file nella galleria dei contenuti personali, salvare in una web map un layer aggiunto da file, oppure eseguire un'analisi in Map Viewer o Scene Viewer.

In tutti e tre i casi il dato viene **copiato**, e la destinazione dipende da cosa si è caricato:

| Destinazione | Caratteristica |
|---|---|
| **Content directory** | Il dato resta un file nella directory dei contenuti del portale, e l'item risultante **non ha un servizio associato**. |
| **Hosting server** | Il dato è archiviato come file sull'hosting server. |
| **ArcGIS Data Store** | Il dato finisce nel relational o nel tile cache data store del base deployment. |

Alcuni esempi concreti di dove finisce cosa:

| Cosa si carica | Item risultante | Dove va il dato |
|---|---|---|
| Shapefile o CSV aggiunto a Map Viewer e salvato nei contenuti personali | Feature layer | Content directory |
| Vector tile package caricato nei contenuti personali | Vector tile layer | Hosting server |
| Un CAD drawing | Item del disegno | Content directory, **senza servizio** |

La riga del CAD è quella che chiarisce il concetto: se nella pagina di dettaglio non compare la sezione con l'URL del servizio, quell'item è un file archiviato, non un servizio interrogabile. Non ci si può costruire sopra una web map.

C'è anche una quarta via che **non copia nulla**: aggiungere un item da un **URL che punta a un endpoint REST**. In quel caso la sorgente originale resta dove sta e il portale la referenzia.

### Rendere gli item trovabili

I **tag** sono ciò che rende un item raggiungibile da chi non sa che esiste, e vanno pensati sul pubblico e sull'uso, non sul contenuto. Un layer di idranti di un'utility idrica non si tagga solo `idranti`: si tagga anche `antincendio`, `acqua`, `utility`, il nome dell'ente e quello della città, perché sono i termini con cui altri dipartimenti lo cercheranno. Un layer di curve di livello destinato a fare da sfondo si tagga `basemap`, perché è la parola che descrive il **ruolo**, non il dato.

## Condividere: livelli e gruppi

Alla creazione, un item è accessibile **solo al suo proprietario**. Chiunque abbia accesso a un item può:

- aprirlo nell'applicazione corrispondente, Map Viewer o ArcGIS Pro;
- condividerlo con un gruppo;
- vederne i metadati;
- **accedere al suo endpoint REST**.

L'ultimo punto merita attenzione da chi sviluppa: concedere accesso a un item significa concedere accesso al suo servizio. Non esiste un livello intermedio in cui la mappa è visibile e l'API no.

I livelli di condivisione sono quattro:

| Livello | Chi accede |
|---|---|
| **Owner** | Solo il proprietario. Gli **administrator** però accedono, modificano e condividono qualunque item del portale. |
| **Group** | Tutti i membri del gruppo. Per condividere con un gruppo bisogna **già esserne membri**. |
| **Organization** | Solo i membri del portale. |
| **Everyone** | Chiunque acceda al sito del portale, se l'accesso anonimo è abilitato. Un administrator può **disabilitare** la condivisione pubblica: in quel caso solo gli administrator possono condividere fuori dall'organizzazione. |

I livelli si combinano con i gruppi, e la combinazione determina chi può propagare l'item: se è condiviso con l'organizzazione, **qualunque** membro può portarlo in un gruppo; se è pubblico, possono farlo anche persone esterne. Condividere in un gruppo un item già pubblico o organizzativo non serve a restringere ma a **evidenziare**: mette il contenuto in una collezione dove chi lo cerca lo trova.

### Creare un gruppo

Un gruppo è una collezione di item legati a una regione, un tema, un dipartimento o un progetto, amministrata dal suo **owner** — trasferibile a un altro membro da un administrator. Vale progettarlo prima di crearlo, su tre assi.

**Informazioni generali**: nome, scopo, tag con cui il gruppo sarà cercabile nel portale.

**Impostazioni**, che definiscono i privilegi dei membri:

- chi può **trovare e vedere** il gruppo nel portale: solo i membri, i membri dell'organizzazione, o chiunque acceda al portale;
- come si **aggiungono** nuovi membri: su invito di un group manager, oppure per richiesta;
- chi può **contribuire** contenuti.

Se un gruppo è visibile ai soli membri, l'adesione può avvenire **solo su invito**: le due impostazioni non sono indipendenti.

**Membri**, ciascuno come *group member* o *group manager*. Il manager ha i privilegi del membro più la possibilità di invitare, processare le richieste di adesione, rimuovere contenuti e membri, e modificare le proprietà del gruppo.

## La decisione centrale: chi gestisce il dato

Pubblicando da ArcGIS Pro si sceglie dove il dato vivrà, e le due categorie sono l'asse su cui ruota tutto il resto.

| | **ArcGIS-managed** | **User-managed** |
|---|---|---|
| Chi controlla il dato | ArcGIS Enterprise o un server stand-alone. | L'organizzazione, fuori da Enterprise. |
| Dove sta | ArcGIS Data Store oppure le directory dell'hosting server. | Database, cartelle o cloud store propri. |
| Come si abilita | Si sceglie **Copy All Data** in pubblicazione. | Si **registra** il data store con un sito ArcGIS Server e si concedono i permessi all'account di ArcGIS Server; poi si sceglie **Reference Registered Data**. |
| Il layer risultante | Un **hosted layer**. | Un layer che **referenzia** il dato registrato. |

### Cosa si guadagna copiando

| Categoria | Vantaggio |
|---|---|
| **Scalabilità** | Sfrutta la capacità del Data Store di scalare su richieste di accesso ed editing. |
| **Accesso al dato** | Elimina i problemi di permessi: l'account di ArcGIS Server ha per costruzione accesso al dato. |
| **Funzionalità** | Abilita raster tile layer e vector tile layer, la pubblicazione di **feature layer vuoti**, il calcolo di valori di un campo in Map Viewer, e la creazione di **hosted feature layer view**. |
| **App** | Necessario per le app che usano per default il relational data store, come **Field Maps** e **Survey123**. |
| **Costi** | Riduce i costi operativi di mantenere una sorgente esterna: geodatabase aziendali, share di rete, storage cloud. |
| **Carichi** | Riduce carico su risorse, rete e server. |
| **Gestione** | Backup e failover forniti dal Data Store; cancellando l'hosted layer vengono **cancellati anche servizio e dato**. |

Il feature layer vuoto è un caso che sembra strano e non lo è: serve a preparare in anticipo il contenitore che un'app di raccolta dati riempirà sul campo.

### Cosa si guadagna referenziando

| Categoria | Vantaggio |
|---|---|
| **Editing multiutente** | Supporta **branch versioning** e **traditional versioning**: più client ArcGIS e non-ArcGIS accedono e aggiornano la stessa sorgente, e le modifiche non finiscono automaticamente nella versione di default, quindi esiste un controllo di qualità. |
| **Aggiornamenti dinamici** | Le modifiche fatte al web feature layer e quelle fatte al dato sorgente si riflettono **in entrambe le direzioni**. |
| **Integrità** | Rende disponibili attribute rule, subtype e domain, contingent value e topologia. |
| **Dataset complessi** | Necessario per geometrie complesse — road network, utility network, trace network — e per dataset grandi come l'imagery. |
| **Gestione** | Referenzia il dato dove è **autorevole**, permette di definire come e dove ArcGIS Server lo raggiunge, e **conserva il dato** anche se il web layer viene cancellato. |

### L'asimmetria che conta: cosa succede cancellando

Le ultime righe delle due tabelle sono lo stesso fatto visto da due lati, ed è il criterio più concreto per scegliere:

- cancellando un **hosted layer** si cancellano servizio **e dato**. Il portale possiede il ciclo di vita del dato;
- cancellando un layer che **referenzia** un data store registrato, il dato resta. Il portale è solo una finestra.

C'è anche un vincolo di dipendenza da conoscere: da un hosted feature layer si possono derivare **feature layer view**, map image layer e tile layer, che referenziano gli stessi dati nel Data Store. Prima di poter cancellare l'hosted feature layer bisogna cancellare **tutti i layer dipendenti**.

### Chi può essere cosa

Non tutti i tipi di layer supportano entrambe le strade.

| Tipo di layer | Copy All Data | Reference Registered Data |
|---|---|---|
| Feature layer | sì | sì |
| Scene layer | sì | sì |
| Map image layer | sì | sì |
| Vector tile layer | sì | sì |
| Imagery layer | sì | sì |
| Web tool | sì | dati sì, ma **gli strumenti** vengono comunque copiati nella directory del Server |
| **Feature layer view** | sì | **no**, solo hosted |
| **Raster tile layer** | sì | **no**, solo hosted |
| **Locator** | sì | **no**, solo hosted |

E, per gli hosted, il dato non finisce sempre nello stesso posto:

| Item | Dove risiede il dato |
|---|---|
| Feature layer, feature layer view | **Relational data store** |
| Scene layer | **Tile cache data store** |
| Map image layer, vector tile layer, raster tile layer, imagery layer, web tool, locator | **Hosting server** |

### Pubblicare in blocco

Quando un data store viene registrato in ArcGIS Pro o in ArcGIS Server, nel portale compare automaticamente un **data store item**. Da lì si può pubblicare in blocco tutto il contenuto di un database, invece di procedere layer per layer.

Come funziona:

- serve prima creare una **cartella** nel portale dove mettere i risultati;
- la pubblicazione crea **un feature layer e un map image layer per ogni feature class e per ogni tabella** del database;
- i layer **referenziano** la sorgente: nessuna copia;
- una volta creati, si condividono come qualunque altro item.

Due conseguenze sui permessi: se il data store item viene condiviso con altri membri, quei membri potranno pubblicare web layer referenziando quel data store; e se la connessione usa **autenticazione del database**, dovranno usare le stesse credenziali.

## Le performance

### Misurare prima di pubblicare

Un layer non ottimizzato produce sintomi riconoscibili: tempi di disegno lunghi in pan e zoom, elaborazioni lente in analisi e geoprocessing, editing pesante, cali di prestazione in certe fasce orarie, carico aumentato su rete, server e database.

In ArcGIS Pro il dato sorgente si misura **prima** di pubblicarlo con l'add-in **PerfTools**, che produce un report con metriche quantitative:

- **draw time**, il tempo di disegno dei layer in pan, zoom e navigazione;
- **edit operation time**, il tempo per creare un numero definito di feature;
- **analysis execution time**, il tempo di esecuzione di un'analisi.

PerfTools itera su **tutti i segnalibri** della mappa e misura quanto ci vuole a renderizzarli, riportando anche i frame per secondo medi. Il ciclo è: aggiungere i dataset a una mappa, misurare, applicare le ottimizzazioni, **rimisurare**. Senza il secondo giro non si sa se l'ottimizzazione ha funzionato.

### Il ruolo del layer

Prima di pubblicare va deciso **che ruolo** il layer avrà nelle mappe, perché è quella scelta a determinare quali ottimizzazioni hanno senso.

| | **Basemap layer** | **Operational layer** |
|---|---|---|
| Quali tipi | Raster tile, vector tile, imagery, e **map image layer come cached map service**. | Feature layer, imagery layer, e **map image layer come dynamic map service**. |
| Scopo | Dati di riferimento sul fondo della mappa. | Capacità interattive: filtri, analisi, raccolta dati. |
| Come funziona | Restituisce tile pre-renderizzati. | Recupera e **ridisegna** il dato a ogni chiamata. |
| Vantaggi | Combina molti layer in un unico sfondo in cache; regge simbologia ed etichette complesse; visualizza rapidamente grandi quantità di dati; scala con impatto minimo su ArcGIS Server. | Interazione con feature e attributi; con i feature layer, **editing**. |
| Da sapere | **Nessun editing web**; gli aggiornamenti dovrebbero essere infrequenti; il **tiling scheme del layer** — scale e sistema di coordinate — viene applicato alla web map. | Il costo si paga a ogni utilizzo, non una volta sola. |

Il punto che genera più confusione è il **map image layer**, che sta in entrambe le colonne: pubblicato come *cached map service* è un basemap, pubblicato come *dynamic map service* è un operational layer. Non è il tipo di item a decidere il ruolo, è come lo si pubblica.

Va notato anche l'ultimo punto della colonna basemap: il tiling scheme del layer **si impone alla mappa** che lo usa. Scegliere un basemap significa scegliere le scale e il sistema di coordinate di tutto ciò che gli si sovrappone.

### Ottimizzare un basemap

Sei tecniche, da applicare perché il layer risulti leggibile a **tutte** le scale messe in cache:

- **scegliere il tipo di cached layer** giusto. In generale il **vector tile layer** è la scelta migliore, ma la funzionalità richiesta può imporne un altro;
- **definire l'area da mettere in cache** in base a scopo e pubblico. La maggior parte dei tipi usa l'estensione di default della mappa; per i map image layer si può definire un'area di interesse;
- **definire il sistema di coordinate** coerente con gli altri cached layer della stessa mappa. Sovrapponendo servizi online — ArcGIS Online, Google Maps, Bing — si usa **WGS 1984 Web Mercator (Auxiliary Sphere)**;
- **configurare le etichette** perché comunichino il riferimento necessario a ogni intervallo di scala del tiling scheme, usando dipendenze di scala e annotazioni;
- **impostare le dipendenze di scala** per mostrare solo i layer rilevanti a ciascuna scala, **allineate agli intervalli** del tiling scheme;
- **ridurre la densità** rimuovendo layer inutilizzati e applicando definition query.

Il terzo punto ha una ragione tecnica che lo rende irreversibile: la **spatial reference di un cached layer è memorizzata con il servizio** e la riproiezione al volo **non è supportata**. Sbagliare sistema di coordinate non si corregge dopo, si ricostruisce.

L'ultimo punto ha un effetto misurabile su due fronti: troppa informazione nella mappa aumenta la **dimensione della cache** e il **tempo per generarla**, oltre a rendere la mappa più difficile da leggere.

### Ottimizzare un operational layer

Qui le tecniche si dividono in due famiglie.

**Visualizzazione:**

- **generalizzare** le feature per migliorare la resa web. Attenzione: generalizzare **rimuove vertici**, quindi va pesato contro l'accuratezza spaziale necessaria e la scala a cui il layer verrà guardato;
- applicare una **simbologia semplice**, che richiede meno tempo per disegnare;
- creare **feature template** per i layer editabili: definiscono le categorie di elementi che chi edita può aggiungere, preservano l'integrità e rendono l'editing più semplice;
- **referenziare la sorgente corretta**: per un feature layer editabile pubblicato per riferimento, conviene registrare la **versione di web editing** del database invece della versione di default;
- **convertire le etichette in annotazioni**. Le etichette si calcolano al volo e rallentano; le annotazioni stanno sempre nella stessa posizione.

**Attributi:**

- **snellire i campi**: identificare quelli necessari a editing, analisi, simbologia e pop-up, e rimuovere tutto il resto. I campi extra si possono riagganciare all'occorrenza con una join da una table layer. Meno campi significa risposta più rapida da ArcGIS Server;
- **costruire indici** sui campi che verranno interrogati: le query diventano molto più rapide e richiedono meno elaborazione;
- **assegnare domini** ai campi, per semplificare l'inserimento e ridurre il numero di valori distinti;
- applicare **definition query** per mostrare solo i dati rilevanti.

Il primo punto è quello che si tende a rinviare, e non conviene: i campi inutili viaggiano su rete a ogni richiesta.

## Comporre la mappa

Una web map è la combinazione di un operational layer e di un basemap layer, e la sua qualità percepita è la somma delle ottimizzazioni fatte a monte su entrambi. Le tecniche si applicano per **requisito**, non per abitudine:

| Requisito del layer | Tecnica |
|---|---|
| Il pubblico deve aggiungere punti compilando gli attributi da liste | Assegnare **domini** ai campi |
| Geometria molto dettagliata, mappa consultata a scala provinciale | **Generalizzare** le feature |
| Mostrare posizione e nome di elementi di riferimento | Configurare le **etichette** |
| Curve principali a tutte le scale, secondarie solo a grande scala | **Dipendenze di scala** |

## Glossario

| Termine | Definizione |
|---|---|
| **Geoinformation model** | Il modello con cui ArcGIS crea e condivide informazione geografica: portal, maps and scenes, layers, analytics, apps, Living Atlas. |
| **Base deployment** | I quattro componenti di ArcGIS Enterprise: Portal for ArcGIS, ArcGIS Server, ArcGIS Data Store, ArcGIS Web Adaptor. |
| **Federation** | Integrazione tra il modello di sicurezza del portale e ArcGIS Server; pubblicando si creano insieme un item e il suo servizio. |
| **Hosting server** | Il Server designato nel base deployment perché sia possibile pubblicare. |
| **Relational / tile cache data store** | Repository del Data Store per i feature layer 2D ospitati / per gli scene layer 3D. |
| **Content directory** | Directory del portale dove risiedono i file degli item **senza** servizio associato. |
| **ArcGIS-managed** | Dato controllato da Enterprise, nel Data Store o nelle directory dell'hosting server; si ottiene con Copy All Data. |
| **User-managed** | Dato che resta in database, cartelle o cloud store propri, reso accessibile registrando il data store. |
| **Hosted layer** | Layer che accede a dati in una posizione gestita da ArcGIS. |
| **Hosted feature layer view** | Vista su un hosted feature layer, per condividere lo stesso dataset con pubblici diversi; disponibile solo su dati ArcGIS-managed. |
| **Data store item** | Item che il portale crea automaticamente quando un data store viene registrato; da esso si pubblica in blocco. |
| **Bulk publishing** | Pubblicazione che crea un feature layer e un map image layer per ogni feature class e tabella di un database registrato. |
| **Branch / traditional versioning** | Modelli di versionamento del geodatabase aziendale che abilitano l'editing multiutente controllato. |
| **PerfTools** | Add-in di ArcGIS Pro che misura draw time, tempo di editing e tempo di analisi di una mappa. |
| **Tiling scheme** | Definizione di scale, dimensioni dei tile e sistema di coordinate di un cached layer; viene applicato alla web map che lo usa. |
| **Cached / dynamic map service** | Le due forme di un map image layer: la prima lo rende un basemap, la seconda un operational layer. |
| **Definition query** | Filtro che limita i dati esposti da un layer, con effetto su leggibilità e performance. |
| **Feature template** | Definizione delle categorie di elementi che chi edita può aggiungere a un feature layer. |
